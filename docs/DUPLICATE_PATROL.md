# Duplicate Patrol and historical enrichment

This isolated development candidate adds useful housekeeping to the existing Navigator, Guided approvals, action journal, image inventory and historical reconciliation engine. It does not grant production access, install itself, or lift the HEXSEED trial's copy-only restriction.

## Try the packaged demonstration

1. Download the Windows candidate from this branch's successful acceptance run. Extract the whole ZIP into a new folder, separate from existing Journey installations. Do not run Setup Journey.
2. Double-click **Start isolated housekeeping demo.cmd**. It starts the included runtime with **Housekeeping checkpoint** inside this extracted folder. Existing Journey data and Windows configuration are not selected. Close any unrelated trial window first so the two interfaces are easy to distinguish.
3. In Inspect, select the included **Housekeeping demonstration/Collection copies** folder. Enable a local checkpoint and proposals. The fourteen files include thirteen invented schematic images, one exact redundant copy, a compressed image variation, and a dependency reference. These are fixtures, not approved CareBloom artwork.
4. Open **Duplicate Patrol and broad organization**, allow reading scoped references, and choose **Audit duplicates**. Expect one proposed exact removal, the retained original, perceptual variations that remain in review, and broad virtual groups. Removal starts locked. The scope and each exact path are visible.
5. For a strictly copy-only trial, stop at this preview. Testing actual removal requires a deliberate new scope permission and then an exact batch approval using your Windows account. This development delivery does not approve that change on HEXSEED. The optional automatic rule is a separate choice; leave it off for the first trial.
6. To test context without physical changes, activate **CareBloom-fixture-pack.json** under Project registry, then preview and import **Local exports** under Local reference history. Expect two exports, five distinct searchable messages, Primrose gaining proposed Heartstone identity, Beat/Melody gaining Musicstone evidence, and the compressed Moonstone export gaining a source relationship. No invented filename grammar becomes approved. Search history for **Primrose Hinamori** to see original conversation timestamps separately from import time.
7. Save plan. The adjacent result identifies the saved inspection snapshot. It includes interpretations and duplicate/organization previews, but does not authorize or schedule execution. An actionable cleanup batch is created separately by **Review selected exact removals as one batch**.
8. Close through **Manage → Close Navigator**. Monitoring and cleanup permissions are session-only. Existing accepted decisions and imports remain in this isolated checkpoint. Reopening the same demonstration reuses it.

If separately authorized for a disposable execution trial, approve the exact redundant copy, verify its absence and the original's continued presence, then use **Review restore** and approve restoration. A new occupant is never overwritten. A before/after native account approval test on HEXSEED remains an operator acceptance task.

## Permissions, storage and patrol

- Exact duplicate groups use streamed SHA-256, including non-image regular files. Hashing refuses unsafe links, changing files and files above 256 MB. A checkpoint hashes at most four new files and reuses up to 64 unchanged records. Files outside the original approved scope are excluded.
- Different image bytes are compared using a difference hash and the existing pixel features. Resizes and compressed exports can be suggested for review. This is approximate visual similarity, not semantic proof of redundancy. Comparisons are bounded to 1,000 images, 20,000 pairs and 100 reported variation pairs; incomplete coverage is disclosed.
- Accepted paths, attributed exemplars, registered protections and dependencies take precedence over copy hints. Scoped references are checked before preparation and again immediately before removal. External dependencies remain the operator's responsibility; the preview never claims global clearance. All near matches are preserved.
- Scope permission requires native account verification, expires after one hour, and disappears on closing/restarting Navigator. Exact batches need their own approval. The optional automatic rule covers only same-folder, same-extension, copy-suffix files with identical bytes and no accepted-path or known reference hold. It is limited to 20 removals per cycle and 100 per grant. Other names and ambiguous variations remain review work.
- Monitoring is opt-in for one scope per session. It performs one bounded discovery/hash checkpoint per minute, without invoking OCR or a model. The initial foreground audit should finish before monitoring. Pause stops queued audits and monitoring. Revocation prevents approved cleanup from executing.
- Each removal is capped at 16 MiB and receives a verified gzip recovery checkpoint. A 256 MiB quota prevents unbounded recovery storage. A batch contains at most 100 copies and remains subject to the existing 50% scope circuit breaker. No permanent duplicate archive is created.
- Previewed recoverable bytes are not guaranteed immediate free disk space: temporary recovery storage has a cost. Checkpoints expire after seven days and are purged when Navigator next performs active housekeeping. An interrupted operation requiring manual recovery is held and its backup is not automatically purged. The interface exposes these states. Such interruptions require review rather than an automatic second removal.
- Restoration requires fresh authorization, a valid checkpoint and an unoccupied original path. There is no generic browser deletion flag or recycle-bin emptying operation. Existing legacy quarantine holds remain in force.

## Historical knowledge and canon

The archive-folder importer already supports complete folder selection, overlap deduplication, source locators, original message timestamps, incremental evidence deltas and selective reassessment. This change adds persistent full-text indexing and search, explicit character identity associations, OCR-linked entity evidence and visible counts. Full text stays local to the chosen checkpoint. Each message is capped at 120,000 characters, with truncation disclosed; structured extraction has separate per-slice budgets. A completed source is searchable only within its authorized project scope. Explicit reimport can backfill text for older structured-only imports without rebuilding accepted decisions.

An accepted identity or purpose remains authoritative over imported proposals. Conflicts are visible in its evidence. An import cannot approve a naming grammar, regenerate approved names, expand permissions, or execute an organization pass. Original filenames and source bytes stay intact. Imported attachment identifiers are references, not recovered image bytes or proof of a hash match. Missing bytes are disclosed.

Broad proposals use recognizable subject or purpose groups. Additional relationships remain searchable evidence instead of creating a mandatory folder hierarchy. Grouping does not wait for perfect filenames.

## Evidence and limitations

`tests/test_duplicate_patrol.py` exercises real removal, recovery, altered keepers, accepted paths, late dependencies, revocation, occupied restore destinations, hash reuse, subsequent monitoring, and recovery expiry. `tests/test_housekeeping_workflow.py` demonstrates the complete authenticated application flow using disposable files and an explicitly labeled fixture actor. Its output is [housekeeping-fixture.json](evidence/housekeeping-fixture.json). `tests/test_housekeeping_history.py` covers before/after interpretation, text search, canon protection, repeat import and legacy backfill. Existing incremental-history acceptance verifies selective reassessment and unchanged-work reuse. `tests/housekeeping_browser.py` tests visible preview, permission boundaries, batch completion, recovery and Save Plan success/failure.

A separate private development checkpoint imported all 27 supplied original JSON exports: 391,506,210 bytes, 88,122 distinct searchable messages, no truncated full-text records, and 4,519 extracted project claims. Reimport reused the index. Seven available original image samples were inspected as copies; history added source/attachment references and a cited Primrose Hinamori association. Source content hashes and modification times, active naming rules and canon were unchanged. Private exports, transcripts and that checkpoint are excluded from this repository.

That result does not establish import into the existing HEXSEED application or reconciliation of its reported 247-file/214-image checkpoint. That live checkpoint is not available in this development environment. Corestone, Touchstone, armory and alias coverage also has controlled fixture acceptance; there is no claim that every historical creative decision has become an executable filename rule.

Linux application/fixture tests and Windows runner acceptance must be reported separately. Native Windows automation uses fixture account attribution, not the operator's actual credentials. Live HEXSEED installation, configuration, real collections and production deletion remain held pending separate authorization.
